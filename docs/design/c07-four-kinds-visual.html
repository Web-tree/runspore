Q20 deferred
How Runspore checks on a herdr step
Drawn: the proposal. The start command runs Claude in herdr under a name made from the step (rs-3f9a…) with the session id it chose, and saves the name, the session id and the machine. The probe asks herdr whether that name still exists: gone means dead; herdr unreachable means unknown, so the step waits for its time limit. A retry starts a new session under the same name that resumes the saved session id.
  • herdr keeps a name with its session when the pane moves; a moved pane gets a new id
  • herdr works across machines, where a local PID means nothing; background Claude keeps Q10's process check
  • risk: detaching herdr from the session by hand clears the name while Claude may still run
Shown in: map interactive box · interactive settings note · interactive lane step 4 · kill lane step 3
Changes these answers make outside C07
  • The map's locked "the person's own session does the step" and CONTEXT.md's In-session step give way to interactive step (herdr); Headless step becomes background step. Q17 Q19
  • C03 used implement as its unsafe example; Claude steps are idempotent now. C03's rule (the declaration decides) stands. Q12
  • Runspore's core: a failed step with no failed path pauses instead of ending the run. A core version bump, and the recorded test runs for that case are redone. Q16 Q22 core change
